## 总体执行流程（4步）

### Step 1：接收计划参数

agent 收到执行指令时，从 prompt 中读取：
- `time_window_days`：分析时间窗口（天数，默认 3）
- `tasks`：已确认执行的子任务 id 列表

### Step 2：串行执行子任务

按 tasks 列表顺序逐个执行：
1. 读取对应子 SOP（`sop_file` 字段指定）
2. 严格按子 SOP 流程操作手机、读取数据
3. 将该子任务结果结构化暂存，格式：
   ```
   [子任务结果: {id}]
   状态: 成功/失败/部分完成
   数据摘要: ...
   评分: X/10
   主要发现: ...
   ```
4. **失败与是否继续下一子任务**：见下文「子任务失败分级」；**同一子任务内**对不可恢复错误必须**果断停重试**，禁止为刷成功而无限换包名/乱点。

**子任务失败分级（执行策略）**

| 类型 | 典型表现 | 本子任务内 | 与后续子任务 |
|------|----------|------------|----------------|
| **A. 全链路阻断** | ADB 断开、未授权调试、设备离线 | 立即结束整次一键分析（见错误处理） | 不再执行 |
| **B. 不可恢复 / 环境不满足** | App **未安装**、包名不存在、MainActivity/入口明确报错、商店页提示未安装、当前手机**客观上无法**完成该子任务 | **最多 1 次**子 SOP 写明的合规备用路径（若有）；若无备用或备用仍报同类错误 → **立刻判定该子任务失败，停止本子任务内一切进一步尝试**（不换未备案包名、不重复同款 launch 超过上述次数） | **可**继续列表中**下一个**子任务（各 App 独立）；不得因上一任务失败而对下一任务「加倍重试」 |
| **C. 可恢复 / 瞬时** | 网络慢、页面未加载完、需一次返回/重进 | 允许子 SOP 规定的**有上限**短重试（如 1～2 次明确操作），超出则按 **B 的失败子任务** 处理，勿空转多轮 |

**子任务间衔接原则：**
- 每个子任务结束后回到手机桌面（`press_key home`），再启动下一个 App
- 子任务间不共享 App 状态

### Step 3：生成综合分析报告

在 Step 2 **结束**时输出综合报告（含：全部跑完、遇 A 类提前终止、或部分子任务 B/C 失败后已按策略停重试并处理完后续项）。**结构固定、子报告数量与顺序随 `tasks` 与子任务注册表动态变化**（对每个在 `tasks` 中的 id 均应有对应小节：成功/部分完成写数据，失败写原因；勿写死为某一两个 App 名称）。

**编排规则：**

1. 按 **Step 1 中 `tasks` 的顺序** 遍历；每个 id 在注册表 JSON 中有对应 `name`，子报告标题用 **`## 子报告 N：{name}`**（N 为 A/B/C… 或 1/2/3…，与执行顺序一致）。
2. 每个子报告的正文结构**由该子任务的子 SOP 与实测数据决定**（例如饮食类可有「订单/营养结构」、压力类可有「周视图统计」、穿戴导出类可有「步数/睡眠摘要」等）。若子 SOP 已规定输出小节标题，优先对齐子 SOP；否则至少包含下列**可复用块**（缺数据则标注未读取，禁止脑补）：
   ```
   【健康/场景评分】⭐… (X/10)  （或该子任务更贴切的评分维度）
   【数据与时间范围】…         （周期、样本量、数据来源 App/导出目录等）
   【主要发现】
     ❌ …  ⚠️ …  ✅ …
   【针对性建议】
     1. …
     2. …
   ```
3. 若某子任务失败：仍保留该 id 对应的一小节，标题可带「（数据未获取）」，`【主要发现】` 首行写失败原因，不写虚构数据。

### Step 4：任务收尾

- 确保手机回到桌面（`press_key home`）
- 不将原始订单明细、原始生理/穿戴明细、可识别隐私片段写入长期记忆（隐私保护）；可记录摘要级结论与方法经验
- 可将综合报告摘要（评分+主要发现）写入 `analyze_lifestyle` 工具记录

## 关键约束

### ✅ 必须做
- 每个子任务结束后回桌面再切 App
- 子任务在 **B/C 类** 失败并记录原因后，**可**继续执行 `tasks` 中下一项；遇 **A 类** 则整单停止
- 对 **B 类**（如 App 不存在）**禁止反复尝试**：达到本节重试/备用上限后立刻收手，进入下一子任务或收尾报告
- 报告使用以上**骨架模板**输出；子报告数量与标题与 `tasks`/注册表一致
- 涉及支付操作必须 ask_user 确认

### ❌ 不要做
- 不要将原始订单/健康明细等可还原隐私的原文写入长期记忆
- 不要在子任务之间共享手机 App 状态
- 不要脑补未读取到的数据
- 不要在报告中作出确定性医学诊断

## 错误处理
- **A 类（ADB/设备）**：立即停止整次一键分析，向用户说明检查 USB、授权、连接；不继续后续子任务。
- **B 类（App 不存在/包无效/明确不可达）**：**不要**在同一子任务上循环尝试多种未在子 SOP 中写明的包名或「再试十次 launch」。按 Step 2 表格：合规备用 **≤1 次**（仅当子 SOP 明确写出）→ 仍失败则**果断结束该子任务**，记录根因；**然后**可执行 `tasks` 中后续独立子任务（若仍有）。最终报告中该子任务小节写清「未执行原因：如未安装 xxx」。
- **C 类（可恢复）**：仅允许子 SOP 或本节隐含范围内的**有限次**重试；若仍失败，**升级为按 B 类收束**（停止本子任务内折腾），不要为凑成功无限占用回合。
- **子任务失败（一般）**：在对应子报告处标注「⚠️ 数据获取失败：[原因]」；综合洞察仅基于**已成功/部分完成**的数据，并单列「未完成任务与建议」（如取消勾选、安装 App、换设备）。
- **数据不完整**：明确标注哪些字段未读取到，不脑补数据
